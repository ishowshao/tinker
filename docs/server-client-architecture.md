# Tinker 常驻 Agent 与 Server / Client 架构演进

记录日期：2026-09-22。

状态：方向讨论稿。本文记录已认可的架构方向、候选迁移步骤和待决问题，
不表示具体接口、进程模型或实施范围已经定稿，也不表示这些能力已经实现。
后续按阶段设计、实施和验收，避免一次性改造难以保证质量。

## 1. 动机与当前基础

Tinker 希望从主要通过终端交互使用的 coding agent，逐步发展为常驻系统、
可以通过 TUI、Web 和 Mobile 访问，并最终能够响应事件和推进长期目标的 agent。
执行任务的生命周期需要独立于任何一个客户端。

当前代码已经存在两条路径：

| 路径 | RuntimeSession 所有者 | 特点 |
| --- | --- | --- |
| 默认 `tinker` | TUI 进程 | 功能完整，退出时释放 runtime |
| `tinker serve` + `tinker connect` / iOS | 服务进程 | 客户端断开不结束任务，但远程能力尚未与默认 TUI 对齐 |

相关代码入口：

- [默认 TUI 组合与生命周期](../src/cli/tui-runner.tsx)。
- [服务端 runtime 创建](../src/cli/serve-runtime.ts)。
- [服务端会话管理](../src/remote/service.ts)与[托管会话执行](../src/agent/runtime-hosted-session.ts)。
- [远程协议](../src/remote/protocol.ts)与[独立远程 TUI](../src/tui/remote-app.tsx)。
- [现有 UIKit 客户端](../client/Tinker/Tinker/)。

Agent 核心已有独立的 runtime 边界；服务端也已有操作回执、请求去重、快照、
增量同步和基于 canonical SQLite 的恢复基础。升级可以在这些基础上演进。
主要工作是统一会话所有权与能力接口，并完善常驻运行语义。

[现有远程访问设计](remote-access-design.md)以保留独立默认 TUI 为前提。
本文提出的长期目标是所有客户端共用服务端，因此会演进这条边界；
迁移完成前，现有行为和兼容性仍需保持。既有远程方案的
[使用说明](remote-access.md)和[验收记录](remote-access-acceptance.md)
不应被理解为本文目标架构已经完成的证据。

## 2. 已认可的三层职责

### Agent core

负责模型循环、上下文维护、工具执行、Skills 和单会话运行机制。
复用现有 runtime、model、context、tools、session 等模块的合理边界。
不承担客户端连接管理或终端界面生命周期。

### Tinker server

负责工作区与会话所有权、任务接收与调度、持久化协调、恢复、交互请求、
客户端同步以及执行资源管理。通过 Agent core 执行任务。

模型凭据、工作区访问和工具执行留在执行主机。Server 可以常驻本机，
架构拆分本身不要求云部署，也不要求立即拆成多个仓库或软件包。

### Tinker clients

TUI、Web、Mobile 都是客户端，负责输入、展示、导航和设备交互，
例如终端快捷键、剪贴板和附件选择。通过统一服务契约提交操作、读取状态和订阅变化。

客户端可有不同的展示和交互能力，但相同业务操作应具有一致语义。
TUI 仍可保持完整而丰富的体验；已有 iOS 项目继续作为 Mobile 入口。

依赖方向为：Clients → Server 服务契约 → Agent core。
具体传输方式、目录拆分和部署形态留待详细设计。

### 实体关系与运行约束

采用单 Server 管理多个 Workspace 的模型，Workspace 下包含多个独立 Session。
Client 与 Session 是连接关系，不拥有 Session 或执行生命周期。

| 实体 | 职责与关系 |
| --- | --- |
| Server | 管理所有 Workspace、Session 和执行资源 |
| Workspace | 提供工作目录和项目环境；不持有全局“当前 Session” |
| Session | 归属一个 Workspace，保存独立的对话历史、上下文和会话配置 |
| Runtime | 承载一个 Session 的执行；每个 Session 最多有一个活动 Runtime |
| Client | 可切换或订阅 Session；同一 Session 可被多个 Client 同时连接 |

- 同一目录启动多个 TUI，默认分别创建独立 Session；打开已有 Session 是显式操作。
- 连接正在执行的 Session 只订阅其状态，不创建第二个 Runtime。
- Runtime 按需加载、空闲时可释放；释放 Runtime 不删除 Session 历史。
- 不同 Session 可并发执行，Server 设置全局并发限制；单个 Session 的状态变更有序处理。
- 当前选中的 Session、输入草稿、滚动位置等属于 Client；已提交消息、执行状态和待处理交互属于 Server。

### 客户端操作语义

| 操作 | 语义 |
| --- | --- |
| 新开对话 | 创建并连接新 Session |
| 打开已有会话 | 连接指定 Session，执行时按需加载 Runtime |
| 切换会话 / 退出客户端 | 切换或解除订阅，不停止执行 |
| 停止任务 | 显式取消指定任务，迟到的请求不得影响后续任务 |
| 删除会话 | 独立的显式生命周期操作 |

第一阶段允许多个 Client 操作同一 Session，由 Server 确定操作顺序，
不引入主控终端转交机制。普通新任务按会话规则排队，运行中追加指示采用独立语义。
交互响应携带交互 ID，仅首个有效响应生效，其他 Client 同步结果并拒绝过期响应。

同一 Workspace 的 Session 共享文件系统。第一阶段保留共享目录行为，
提供同工作区活动会话的查询能力，不承诺跨 Session 的文件修改隔离。
在 TUI 中增加相关展示须遵循下述 UI 约束。
独立 worktree 等隔离策略留待后续设计。

## 3. 永久运行 Agent 的两个阶段

### 第一阶段：服务常驻，执行独立于客户端

服务随时接收任务，已接受的任务不依赖客户端在线。
关闭终端、手机锁屏、网络断开或切换会话，仅影响连接和展示。
重新连接后可以恢复查看历史、任务状态和待处理交互。

需要分别定义：

- 客户端断开：解除订阅，不停止任务。
- 停止任务：显式、针对特定任务的服务端操作。
- 关闭服务：处理正在执行的任务、子进程、持久化和恢复状态。

常驻的是服务及其接收工作的能力；空闲时不需要持续调用模型。

### 第二阶段：事件驱动和长期目标

在第一阶段稳定后，支持定时器、文件变化、外部事件等触发来源，
以及跨多次执行推进的长期目标。

需要进一步设计：

- 持久化任务队列、触发器和调度状态。
- 长期目标与具体执行任务、会话、Turn 的关系。
- 执行预算、并发限制、失败退避、暂停与停止条件。
- 无客户端在线时的待确认处理，以及完成或需要介入时的通知。
- 重复事件、服务停机期间错过的触发和重启后的恢复策略。

这些能力属于目标方向；第一阶段只需保留合理边界，不一次性实现完整调度系统。

## 4. 迁移中的关键约束

### TUI 视觉与交互保持不变（硬约束）

本次升级保留现有完整 TUI 的视觉与交互，仅替换底层运行依赖和通信方式。

- 保留布局、样式、消息与工具展示、流式输出效果。
- 保留快捷键、输入编辑、命令、导航和会话切换体验。
- 继续使用现有完整 TUI，不以简化的 `RemoteApp` 替换。
- 改造集中于 controller、客户端适配器和服务端；组件内部确需调整时，外部表现保持一致。
- 已认可的生命周期变化是退出 TUI 或切换会话不再结束后台任务。
- 连接失败、重连等新增状态优先使用现有提示区域；新增或改变用户交互须先与用户确认。

每批 TUI 迁移均须验证视觉与交互回归，不能仅以协议测试和任务执行成功作为验收依据。

### 能力对齐与服务契约

现有远程协议主要支持创建、接管、发送消息、停止、回答和确认。
默认 TUI 还拥有图片输入、上下文维护、撤销、克隆会话、模型切换、推理强度、
运行中追加输入和 provider 重试交互等能力，需要逐项明确服务端语义。

不能直接用当前简化的 `connect` 界面替换完整 TUI。
应先建立能力清单和统一契约，再逐步迁移现有 TUI 的底层依赖。
协议需要明确版本、能力协商、错误、附件传输和过期操作处理，
避免把 runtime 内部对象和方法原样暴露到网络。

现有 HTTP 服务拒绝带 `Origin` 的请求。Web 客户端接入还需要专门设计
浏览器认证、来源校验和连接方式。

### 所有权、多端操作与工作区并发

每个会话只有一个执行所有者，客户端可以有多个。
提问和确认属于服务端状态，客户端通过交互 ID 回答；一端处理后，
其他端同步结果，旧答案不能作用于新的交互。

同一会话的状态修改需要有明确顺序。不同会话可以并行，但它们可能修改同一工作区，
仍需设计冲突策略；会话所有权本身不能解决文件修改冲突。
客户端发来的普通排队任务和对正在运行任务的追加指示，也需要区分语义。

### 会话、任务与执行资源

会话承载长期历史，任务表达需要执行的工作，runtime 是运行时资源。
未来长期目标还可能跨越多个任务。任务模型尚待设计，不能直接等同于当前 Turn。
既有概念见 [Session / Turn / Frame / Message](session-turn-frame-message-concepts.md)。

当前服务启动会打开已初始化的托管会话，并有 128 个托管会话的数量限制。
长期运行需要按需加载、空闲卸载和全局资源限制，避免历史会话数量持续放大
内存、MCP 连接和子进程占用。卸载空闲 runtime 与删除会话历史应有不同语义。

### 持久化、同步与恢复

Canonical SQLite 仍是会话恢复的事实来源；流式文本和临时运行视图应明确区分。
客户端通过快照和有序增量同步，处理游标失效、重复事件、断线及服务重启。
慢客户端不应阻塞执行。

当前服务重启后将未完成操作标记为 `interrupted`，不会自动重放。
后续应区分尚未开始的排队任务、已开始执行的任务和结果不确定的外部操作。
请求去重不等于工具副作用只发生一次；例如 shell 命令可能已经完成，
但完成记录尚未持久化。自动恢复必须明确安全边界，不能承诺任意执行透明续跑。

## 5. 分阶段实施与验收

按可独立验收、稳定使用的阶段推进。每阶段开始前明确改动范围、保留行为、验收条件
和回退方式；完成验证后再决定下一步。以下实施步骤仍可继续拆小，不一次性落地。

### 第一阶段目标：服务常驻

| 实施步骤 | 范围 | 主要验收目标 |
| --- | --- | --- |
| 1：统一运行配置 | 收拢默认 TUI 与服务端的 runtime 创建逻辑，盘点能力差异 | 两条路径保持现有行为，配置与能力差异有明确归属 |
| 2：建立完整客户端边界 | 定义会话操作、状态快照、订阅和交互契约；现有完整 TUI 通过本地适配器使用接口 | TUI 表现不变，不再直接持有 runtime、访问会话存储或管理执行生命周期 |
| 3：完整 TUI 接入服务 | 实现服务端适配，逐项迁移完整 TUI 的底层调用 | 可选择服务模式运行完整 TUI，能力逐项对齐，旧入口仍可用 |
| 4：验证多端与恢复 | 对齐 iOS，验证多端操作、重连、去重和服务重启 | 终端退出后任务继续，手机能接手，重连状态一致，重启不误重放 |
| 5：默认服务化 | 默认入口连接本机服务，完善发现、启动和旧会话接入 | 日常启动便利，会话所有权唯一，默认入口正式切换 |
| 6：完善常驻运行 | 系统托管、按需加载、空闲回收、并发限制、关闭及升级策略 | 长时间运行资源可控，故障和升级过程有明确行为 |

步骤 2、3 按功能组逐批完成契约、实现与验收：

1. 会话创建、连接、历史和状态订阅。
2. 提交任务、流式输出、工具状态、停止和运行中追加输入。
3. 用户提问、命令确认和 provider 重试交互。
4. 图片、上下文维护、撤销、克隆和模型配置。

本地适配器是过渡实现，可在当前进程调用 runtime，但契约从一开始即适应异步服务调用。
先验证职责拆分，再接入网络与服务进程。默认路径统一后移除不再需要的过渡实现，
避免长期维护两套业务逻辑。

完整能力与多端验收通过，并经过实际持续使用后，才切换默认入口。
步骤 1 不改变默认启动方式，不引入新的任务调度系统。

#### 步骤 1：创建逻辑与能力归属

默认 TUI 与服务端共用 [interactive-runtime.ts](../src/cli/interactive-runtime.ts)，
集中组装模型与 refiner 共用的 reasoning controller、项目指令、Skills、上下文配置、
工具配置、事件输出及 runtime 创建参数。每次创建或恢复重新加载指令和 Skills。
入口保留配置选择、工作区规范化、历史投影及生命周期职责。

| 配置或能力 | 默认 TUI | 当前服务路径 | 职责归属与后续边界 |
| --- | --- | --- | --- |
| 配置加载 | 启动时解析，按选定 profile 派生 | 每次创建 runtime 按 workspace 配置解析 | 入口负责配置来源，共享工厂接收已解析配置 |
| 恢复 profile | 从会话摘要选择 | 从会话摘要选择，优先于工作区的新会话 profile | 入口负责会话选择与兼容校验 |
| 工作区与存储 | 入口 realpath，使用默认存储根 | 使用服务已规范化的工作区及显式 homeRoot | 入口负责路径与所有权，共享工厂原样传递 |
| 模型、上下文、指令、Skills、工具配置 | 使用共享创建逻辑 | 使用共享创建逻辑 | 创建逻辑集中；provider 与执行规则仍在原模块 |
| AskUser / Bash 确认 | 启用交互 | 启用交互 | core 持有交互；两入口当前均使用交互式 guard 语义 |
| 文件撤销 | 启用 | 未启用 | 共享工厂显式保留入口策略；后续补齐服务操作 |
| Provider 重试交互 | 启用 | 未启用 | 共享工厂显式保留入口策略；后续补齐交互协议 |
| 图片、手动上下文维护、克隆、模型与推理强度操作 | 完整 TUI 提供入口 | 远程协议尚未完整暴露 | 后续客户端契约与服务操作负责对齐 |
| 运行中追加输入 | runtime prompt scheduler | 托管层将普通 prompt 排队为后续 Turn | 后续协议明确区分追加指示与新任务 |
| 历史与展示 | TUI projection / resume reader | canonical history reader / 远程同步视图 | 保持各自投影，共享创建逻辑不接管展示 |
| 执行生命周期 | TUI controller 持有并释放 | HostedSession 持有并释放 | 本步骤保持现状，后续再统一服务所有权 |

one-shot CLI 的执行与输出策略保持独立，本步骤不迁移。
本步骤不修改 TUI 组件、默认入口、远程协议或服务调度行为。

步骤 1 实施验证（2026-09-22）：`bun run check:fast` 与完整 `bun run check` 通过；
完整门禁包含 1302 个通过测试、真实进程 PTY TUI 回归及 benchmark smoke。
新增组合测试覆盖两种入口的能力策略、新建与恢复、指令重新加载，
以及服务端实际创建入口的配置解析和同一数据库历史恢复。
该结果不代表后续客户端解耦或默认服务化已经实施。

#### 步骤 2：本地客户端边界

- [session-client.ts](../src/client/session-client.ts) 定义 `SessionClient<View>`、
  `WorkspaceClient<View>` 和 `ClientConnection<View>`，覆盖会话操作、状态读取与订阅、
  任务提交、交互响应、图片、上下文维护及配置操作。
- 同步读取返回客户端当前快照；所有命令通过 Promise 返回结果或失败。
  展示视图由泛型参数提供，客户端契约不依赖 Ink 或 TUI 投影实现。
- [local-workspace-client.ts](../src/client/local-workspace-client.ts) 封装本地 runtime
  和 SessionCatalog，保留操作串行化、切换前准备目标及失败清理策略。
  对外 binding 不包含 runtime 或释放执行实例的接口。
- [local-tui-client.ts](../src/cli/local-tui-client.ts) 在组合层创建本地适配器，
  负责新建、恢复、profile 选择和历史投影初始化。终端 runner 只创建客户端连接、
  渲染界面并关闭连接，不再直接创建 runtime 或访问会话存储。
- TUI 使用只读投影接口，保留原有渲染及流式展示；`/copy` 通过客户端查询回复。
  推理强度、YOLO 和追加输入等待客户端操作结果后再反馈成功或失败。

这是进程内客户端 API，不是网络线协议；Promise、AbortSignal 和界面切换回调
不直接序列化传输。后续服务端适配负责映射请求、取消、快照和状态订阅，
并将服务错误转换为客户端可处理的错误语义。

本步骤保留本地适配器在关闭连接、切换会话时释放 runtime 的旧策略，
不提前启用后台常驻语义。关闭连接和显式取消任务在契约中分离，
服务端适配接入后再实现断开仅解除订阅。现有远程协议与默认启动方式保持不变。
客户端本地的输入历史、剪贴板等能力继续由终端组合层提供。

步骤 2 实施验证（2026-09-22）：`bun run check:fast` 与完整 `bun run check` 通过；
完整门禁包含 1306 个通过测试、真实进程 PTY TUI 回归及 benchmark smoke。
新增测试覆盖客户端不暴露 runtime 所有权、异步操作失败、等待确认后反馈结果，

#### 步骤 3 第一批：服务会话、历史与状态订阅

通过显式入口使用现有完整 TUI：

```sh
tinker connect --config <client.json> --tui --workspace <workspace-id>
tinker connect --config <client.json> --tui --workspace <workspace-id> --session <session-id>
```

不指定 Session 时创建独立会话；指定时连接该工作区的已有会话。
`/clear` 创建新会话，`/resume` 列出并连接已有会话。服务托管的活动会话可直接连接；
本地会话仍须先退出原执行进程，再由服务接管。切换与退出只关闭客户端订阅。
每个终端独立维护选中会话，不读写旧远程客户端的共享选择状态。
默认 `tinker` 与不带 `--tui` 的旧 `connect` 入口保持原行为。

- `RemoteWorkspaceClient` 实现既有客户端接口，不创建本地 runtime，不读取本地会话库。
- 增加 `/v1/workspaces/:id/tui-sessions` 和 `/v1/sessions/:id/tui-snapshot` 只读接口；
  复用现有认证及工作区校验，不改变旧同步协议或 iOS 入口。
- 历史复用 canonical SQLite 的完整 TUI 投影，保留工具、差异及图片提示等既有历史格式，
  使用与本地恢复一致的最近回合和条目上限。未完成回合不伪装成已完成历史。
- WebSocket 通知驱动历史与状态刷新；连接状态在既有 live 展示区域呈现。
  重连保留已有历史并补齐新内容，避免重复打印；刷新失败保留最后有效视图并重试。
- 当前批次展示已完成回合历史及服务执行状态。任务提交、停止、运行中追加输入、
  流式文本、活动工具详情、交互响应及其他写操作留待后续批次；未接入操作明确拒绝，
  不回退到本地执行。远程文件和 Memory 浏览也不读取客户端同名路径。

手动验收：先启动更新后的服务，再用上述入口连接；验证历史展示、`/clear`、`/resume`
和 `/quit`。可用现有 iOS 或旧 `connect` 在同一会话发起任务，观察完整 TUI 的状态与
完成后的历史更新；断开、重连以及关闭一个终端不得取消服务端任务。

第一批实施验证（2026-09-22）：`bun run check:fast` 和完整 `bun run check` 通过，
1309 个测试通过，包含 HTTPS/WebSocket 多客户端与重连测试，以及完整 TUI 的真实
PTY 会话创建、历史恢复和退出验收；benchmark smoke 与打包文件检查通过。
原有本地 TUI、远程服务和 iOS 协议的回归测试继续通过；本批未进行 iOS 真机验收。

### 第二阶段目标：自主触发与长期目标

| 实施步骤 | 范围 | 主要验收目标 |
| --- | --- | --- |
| 7：持久化任务 | 用户手动提交，明确任务状态、排队、取消、预算和恢复策略 | 接收、执行与恢复语义可验证，结果不确定的任务不误重放 |
| 8：自主触发 | 先接入一种触发来源，再逐项扩展 | 去重、退避、停机补偿和停止条件明确 |
| 9：长期目标 | 在任务系统上增加进度、后续任务安排、暂停、停止和用户介入 | 目标推进受预算和生命周期约束，状态可恢复、可解释 |

任务系统先于触发器建立，各触发来源共用执行和恢复机制。

### 验收要求

第一阶段的关键端到端验收场景：

1. TUI 发起任务，确认服务已经接受后退出。
2. 任务继续执行；手机能够看到进度并处理需要用户回答的交互。
3. 重新打开 TUI，接回同一会话并看到一致状态。
4. 分别验证断网、客户端终止和服务重启；服务重启后的中断状态必须准确，
   不以自动重复执行来掩盖恢复问题。

验收应覆盖现有 TUI 的视觉、交互与能力回归，以及真实客户端生命周期，
不能只靠编译成功或协议单元测试。涉及手机生命周期时须使用真实设备验证。
每个实施阶段均遵循项目 `AGENTS.md` 的完整质量门禁，并完成对应的真实使用验证。

## 6. 待继续思考的问题

具体 API、命令行变化、目录结构、传输选型和任务模型在后续阶段单独讨论确定。
